## 1. 从发展到系统组成
### 1.1 一条简短的历史线索
讲义用器件与系统形态的变化划分计算机世代，重点不是背年份，而是理解**器件进步如何推动软件与系统结构进步**。

| 阶段 | 大致时期 | 讲义强调的特征 |
|---|---|---|
| 前计算机 | 1946 年以前 | 非电子、不可编程的计算辅助装置 |
| 第一代 | 1946—1956 | 电子管，可编程 |
| 第二代 | 1956—1964 | 晶体管，体积、功耗、可靠性改善，符号语言发展 |
| 第三代 | 1964—1971 | 集成电路，操作系统与分时系统发展 |
| 第四代 | 1971 年至今 | 微处理器、个人计算机、图形用户界面 |
| 第五代 | 未来 | 尚无统一公认的世代定义 |

这条线索中有几个值得分清的事实：
- 1642—1645 年，Pascal 研制机械计算器，乘除法通过重复加减实现。
- 1936 年，Turing 用图灵机形式化计算与算法概念；图灵机是理论模型，不等同于某台现代 PC。
- ABC（Atanasoff–Berry Computer）采用二进制和电子运算，但它是专用、不可编程、非图灵完全的设备。
- ENIAC 是通用、可编程、图灵完全的电子计算机，但采用**十进制**，不能把它误记成现代二进制存储程序计算机的同义词。
- 微处理器把整个 CPU 集成到芯片上；它是集成电路技术发展的产物，并不是“用微处理器替代集成电路这种技术”。
- RISC 通过较规则的指令与实现思路改善设计和执行效率，但不能笼统推出“RISC 的所有程序都更快”或“CPI 必然为 1”。
### 1.2 冯·诺依曼结构：抓住存储程序即可
冯·诺依曼结构的关键图景是：
1. 运算与存储在概念上分离。
2. **指令与数据都存放在存储器中**，程序可以预先存储并由机器逐条执行。
3. 系统具有输入、输出机制。
4. 指令集规定软件可以要求硬件执行什么操作。
“指令与数据存放在同一存储器中”描述的是体系结构层面的存储程序思想。
它不意味着现代处理器的 L1 指令 Cache 与数据 Cache 在物理上必须合并，也不意味着指令和数据在任何时刻都走完全相同的物理通路。

本课程更关心的是：程序如何经指令集落到数据通路，存储与 I/O 如何参与执行，以及这些组织方式怎样影响性能。
### 1.3 五类经典硬件部件
一台完整计算机可先从功能上拆成五类部件：

| 部件 | 主要职责 | 例子或说明 |
|---|---|---|
| 输入（input） | 向计算机送入程序与数据 | 键盘、触摸屏、摄像头、麦克风 |
| 输出（output） | 把结果呈现给用户或送往另一系统 | 显示器、扬声器、网络接口 |
| 存储器（memory） | 保存正在运行的程序及其数据，也可长期保存信息 | Cache、主存、Flash、磁盘 |
| 数据通路（datapath） | 对数据执行算术、逻辑、传送等操作 | ALU、寄存器、MUX、总线 |
| 控制单元（control） | 根据指令产生控制信号，协调数据通路、存储器与 I/O | 指令译码、状态与控制逻辑 |

数据通路与控制单元共同组成 CPU 的核心。
“CPU 会计算”只是其中一半；另一半是**在正确的时刻让正确的部件执行正确的操作**。
```text
计算机系统
├── 软件 software
│   ├── 应用软件
│   └── 系统软件：操作系统、编译器等
└── 硬件 hardware
    ├── CPU
    │   ├── 控制单元 control unit
    │   └── 数据通路 datapath
    │       ├── 多路选择器 MUX
    │       ├── ALU：加法器、逻辑单元、乘法器等
    │       └── 寄存器 registers
    ├── 存储器 memory
    └── I/O 接口与设备
        ├── 输入：键盘、鼠标、触摸屏
        ├── 双向：USB、网络接口
        └── 输出：显示器、扬声器
```
![[co-ch1-W4yzeDdV.png]]

这张图把原理框图落到了实验板：CPU 内有控制器与数据通路，ROM/存储器保存程序或数据，PS/2、VGA 等接口连接外部设备。
它体现的是后续实验要搭建和联调的**系统关系**，不只是孤立的 ALU。
### 1.4 CPU、存储器与 I/O 怎样协作
**CPU：主动执行指令的部件。**
- 数据通路完成加法、比较、移位、寄存器传送等具体操作。
- 控制单元根据当前指令与机器状态产生控制信号。
- CPU 还会发出存储器访问和 I/O 操作所需的控制信息。
- 同一 ISA 可以对应单周期、多周期、流水线等不同实现，不能把 ISA 与某一种数据通路画等号。
**存储器：程序与数据的存放空间。**

| 类型 | 易失性 | 常见角色 | 相对特征 |
|---|---|---|---|
| SRAM | 易失 | Cache | 快、每位成本高、容量通常较小 |
| DRAM | 易失 | 主存 | 容量较大，速度低于片上 SRAM |
| Flash | 非易失 | SSD、移动设备存储、固件存储 | 可掉电保存，访问特征不同于 DRAM |
| 磁盘 | 非易失 | 大容量二级存储 | 容量大、每位成本低，延迟较高 |

- **主存（main memory）**保存运行中的程序和数据，讲义以 DRAM 为例，强调其易失性。
- **二级存储（secondary storage）**在多次运行之间保存程序与数据，讲义以 Flash 和磁盘为例。
- “随机访问”不表示访问内容随机，而是指可按地址直接访问；也不要把 DRAM 的 Dynamic 误解为“数据会随机变化”。
- 显示器的帧缓冲区（frame buffer）保存像素内容，显示设备把它呈现为图像，这是存储器与 I/O 协作的典型例子。
**I/O：连接计算机与外部世界。**
- 输入设备把外部信息送入系统，输出设备把计算结果送出。
- 网络接口、USB 等通常支持双向传输，不应硬塞进“只能输入”或“只能输出”。
- 移动设备中触摸屏、摄像头、无线通信等占据大量系统资源，说明整机性能绝不等同于 CPU 性能。
- I/O 设备通常经控制器或接口接入系统，软件还依赖操作系统与驱动程序使用它们。
### 1.5 芯片制造、成本与摩尔定律
处理器和存储器都由集成电路构成。
讲义给出的制造主线是：芯片设计、晶圆生产、晶圆测试、切片、封装和成品测试。

在固定晶圆成本与工艺条件下，可以用下面的近似关系理解芯片面积为何重要：
$$\text{Dies per wafer} \approx \frac{\text{Wafer area}}{\text{Die area}}$$
$$\text{Cost per die} \approx \frac{\text{Cost per wafer}}{\text{Dies per wafer}\times\text{Yield}}$$
讲义还采用如下经验良率模型：
$$\text{Yield} \approx \frac{1}{\left(1+\dfrac{\text{Defects per area}\times\text{Die area}}{2}\right)^2}$$
其中：
- **die** 是晶圆切割出的单个裸片，封装后才成为常见意义上的芯片产品。
- **良率（yield）**是合格裸片所占比例，不是“晶圆面积利用率”。
- 缺陷密度主要由制造工艺影响，裸片面积受体系结构、电路和版图设计影响。
- 面积增大既可能减少每片晶圆的裸片数，也可能降低良率，因此成本与面积不是简单线性关系。
- 上述良率式是课程采用的近似模型，不应把它当成适用于所有工艺的普适物理定律。
**摩尔定律**最初是对集成度增长趋势的经验观察，讲义表述为单芯片可集成晶体管数量约每两年翻一番，教材也常见 18—24 个月的说法。
它不等于“程序速度必然两年翻倍”，更不是永远成立的物理定律。
工艺缩放带来资源、成本与功耗机会，同时也带来制造精度、复杂度和物理极限的挑战。

## 2. 系统层次与 ISA 契约
### 2.1 软件也分层
计算机系统不是“应用程序直接控制晶体管”，而是由多层抽象共同工作：
- **应用软件**面向用户任务，例如文档处理、演示和计算程序。
- **操作系统**处理基本 I/O，分配存储与内存，在多个程序之间调度与共享机器资源。
- **编译器**把高级语言程序翻译成面向目标机器的低级代码。
- **固件（firmware）**通常指设备中较贴近硬件、相对固定的软件；**驱动程序**则是操作系统管理设备的软件模块。二者相关，但不应完全当作同义词。
抽象的价值是：下层把复杂实现细节封装起来，上层只依赖较简单、稳定的模型。
这既降低设计难度，也允许不同层次独立优化。
### 2.2 从高级语言到机器语言
以讲义中的 C 语言 `swap` 为例，典型翻译链条为：
```text
高级语言程序（C）
      │
      │ 编译器 compiler
      ▼
汇编语言程序（助记符与符号地址）
      │
      │ 汇编器 assembler
      ▼
二进制机器语言程序（指令编码）
      │
      │ 处理器取指、译码、执行
      ▼
数据通路、存储器与 I/O 的实际动作
```
- 高级语言更接近问题表达，有利于提高开发生产率，并减少对特定机器细节的依赖。
- 汇编语言用助记符表示指令，例如 `add`；汇编器负责把汇编指令编码为机器指令。
- 机器语言最终用二进制编码表达操作类型、寄存器、立即数或地址等信息。
- 实际工具链还可能包含链接器和加载器；讲义此处的重点是编译与汇编所展示的层次关系。
- “硬件只理解二进制”不表示硬件理解二进制数的抽象数学意义，而是电路对高低电平及其编码作出响应。
### 2.3 ISA 是软硬件之间的契约
**指令集体系结构（Instruction Set Architecture，ISA）**是硬件与最低层系统软件之间的接口。

它约定软件可见的机器状态与指令行为，例如：
- 有哪些指令，每条指令做什么。
- 指令怎样编码，操作数怎样指定。
- 软件可见的寄存器、数据类型与寻址方式。
- 存储器访问以及异常、控制转移等对软件可见的基本语义。
![[co-ch1-XwDLgWQh.png]]

可以把这层契约概括为：

> 软件按照 ISA 表达“要做什么”；微体系结构决定“用怎样的数据通路、控制和时序把它做出来”。

| 层次 | 回答的问题 | 举例 |
|---|---|---|
| ISA | 对软件承诺什么 | 指令语义、寄存器、编码、寻址 |
| 微体系结构（microarchitecture） | 怎样组织实现 | 单周期、流水线、Cache 组织、发射宽度 |
| 电路与工艺实现 | 怎样用物理器件完成 | 逻辑门、晶体管、布线、制造工艺 |

**为什么同一 ISA 很重要？**
因为多种成本和性能不同的实现可以运行相同的机器级软件。
只要保持所要求的指令语义，底层可以从单周期改为流水线，而上层不必因数据通路变化而重写每条指令。

但“ISA 相同”不等于任何二进制程序都能无条件跨系统运行。
可执行文件格式、操作系统 ABI、系统调用和外部设备环境仍可能不同；解释型语言还依赖相应运行时。
ISA 是关键契约，不是软件可移植性的全部。

本课程后续会在 [[03 RISC-V 指令系统]] 具体研究这层接口，在 [[04 处理器：单周期与流水线]] 研究同一接口下的不同实现。

## 3. 性能的基本度量
### 3.1 响应时间与吞吐率不是一回事

| 指标 | 定义 | 典型问题 |
|---|---|---|
| 响应时间（response time）/ 执行时间（execution time） | 完成一个任务所花的时间 | 这次计算多久结束 |
| 吞吐率（throughput） | 单位时间完成的总工作量 | 每小时完成多少任务或事务 |

讲义也使用 bandwidth 指吞吐率；在存储和网络语境中，带宽还可能特指单位时间传输的数据量，要结合上下文判断。

对讲义提出的两个设想，应这样分析：
- **换用更快的处理器**：若任务确实受益于处理器加速，单任务响应时间通常缩短；在连续有任务到达时，单位时间可完成的任务数也可能增加。
- **增加处理器**：通常更容易提升多任务吞吐率；单个任务若不能并行，响应时间未必缩短，通信、同步和负载不均还可能带来额外开销。
因此，二者**不是倒数关系，也不能无条件互相换算**。
流水线常提高指令吞吐率，但寄存器分割和控制开销可能使单条指令的实际延迟增加。
缩短时钟周期只有在周期数等条件明确时才可用于推断响应时间改善，不能脱离程序与实现单独下结论。
### 3.2 性能与相对性能
对以执行时间衡量的同一任务，定义：
$$\text{Performance}_X=\frac{1}{\text{Execution time}_X}$$
若“$X$ 比 $Y$ 快 $n$ 倍”，则：
$$n=\frac{\text{Performance}_X}{\text{Performance}_Y} =\frac{\text{Execution time}_Y}{\text{Execution time}_X}$$
这个比值的成立前提是：两台机器完成**同一个任务**，并用相同口径测量时间。
如果工作量不同，单独比较两个时间的倒数没有公平意义。

> [!warning] 分子分母不要颠倒
> $X$ 更快，所以 $\text{Execution time}_X$ 更小，$\text{Execution time}_Y/\text{Execution time}_X$ 才大于 1。
> 中文“快 $n$ 倍”在口语中偶有歧义，做题最好直接写“性能为 $n$ 倍”或“执行时间变为原来的 $1/n$”。

**讲义例：同一程序在 A 上运行 10 s，在 B 上运行 15 s。**
$$\frac{\text{Performance}_A}{\text{Performance}_B} =\frac{15\ \text{s}}{10\ \text{s}}=1.5$$
所以 A 的性能是 B 的 1.5 倍，执行时间则是 B 的 $10/15=2/3$。
“性能提高 50%”与“时间减少 50%”不是同一句话；本例时间减少的是 $1/3\approx33.3\%$。
### 3.3 墙上时间与 CPU 时间
- **持续时间（elapsed time）/ wall-clock time**：任务从开始到结束经历的全部时间，包括处理、I/O、OS 开销、等待与其他任务共享机器的影响。
- **CPU 时间（CPU time）**：CPU 实际用于该任务的时间，不包含该任务等待 I/O 或被其他任务占用 CPU 的时间。
- **用户 CPU 时间（user CPU time）**：执行用户态代码所花的 CPU 时间。
- **系统 CPU 时间（system CPU time）**：操作系统为该任务服务所花的内核态 CPU 时间。
在本笔记采用的无重叠计账口径下：
$$\text{Task CPU time}=\text{User CPU time}+\text{System CPU time}$$
墙上时间反映用户实际等待，CPU 时间帮助隔离处理器与程序执行成本。
磁盘密集型程序与计算密集型程序对“换更快 CPU”的响应不同，原因之一就在于此。
多核并行计账时还可能出现多个核同时工作的情形，必须先说明统计口径，不能机械把所有核的 CPU 时间相加后当作用户等待时间。
### 3.4 时钟周期、频率与单位
数字硬件由时钟协调状态更新：
- **时钟周期（clock period / clock cycle time）**是一个时钟循环的持续时间，单位是秒。
- **时钟频率（clock rate / frequency）**是一秒内的时钟周期数，单位是 Hz。
- **时钟周期数（clock cycles）**是程序执行需要的周期总数，是一个计数，不是时间。
$$\text{Clock rate}=\frac{1}{\text{Clock cycle time}}$$
常用换算：

| 量 | 换算 |
|---|---|
| $1\ \text{ns}$ | $10^{-9}\ \text{s}$ |
| $1\ \text{ps}$ | $10^{-12}\ \text{s}$ |
| $1\ \text{GHz}$ | $10^9\ \text{Hz}$ |
| $1\ \text{MHz}$ | $10^6\ \text{Hz}$ |

例如 $250\ \text{ps}=0.25\ \text{ns}=250\times10^{-12}\ \text{s}$，其倒数为 $4\ \text{GHz}$。
频率高并不自动意味着程序快，因为程序周期数可能不同。

## 4. CPU 时间与性能铁律
### 4.1 从周期数到程序执行时间
CPU 执行时间首先可写为：
$$\text{CPU time}=\text{CPU clock cycles}\times\text{Clock cycle time} =\frac{\text{CPU clock cycles}}{\text{Clock rate}}$$
改进方向只有两类：减少程序所需周期数，或缩短每个周期的时间。
但硬件设计者经常需要在两者之间权衡，而不是同时无成本地改善。

**完整例题 1：提频导致周期数增加。**

计算机 A 的时钟频率为 $2\ \text{GHz}$，运行某程序的 CPU 时间为 $10\ \text{s}$。
新设计 B 的目标时间为 $6\ \text{s}$，但设计变化使时钟周期数变为 A 的 $1.2$ 倍。
求 B 至少需要多高的时钟频率。

第一步，求 A 的周期数：
$$N_A=f_A T_A=(2\times10^9\ \text{Hz})(10\ \text{s})=2.0\times10^{10}$$
第二步，求 B 的周期数：
$$N_B=1.2N_A=2.4\times10^{10}$$
第三步，由 $T_B=N_B/f_B$ 求频率：
$$f_B=\frac{N_B}{T_B}=\frac{2.4\times10^{10}}{6\ \text{s}}=4.0\times10^9\ \text{Hz}=4.0\ \text{GHz}$$
结论是 B 需要 $4.0\ \text{GHz}$。
频率虽然翻倍，时间却只从 $10\ \text{s}$ 降为 $6\ \text{s}$，因为周期数同时增加了 20%。

**常见误区：**直接用 $2\ \text{GHz}\times10/6$ 得到答案却忽略 $1.2$；或者认为频率翻倍，执行时间就必然减半。
### 4.2 指令数、CPI 与性能铁律
对给定程序的执行：
- **指令数（Instruction Count，IC）**：动态执行的机器指令条数，不是源文件行数，也通常不是静态代码长度。
- **CPI（Cycles Per Instruction）**：平均每条指令所需时钟周期数。
- **时钟周期时间（$T_c$）**：一个周期持续多久；其倒数是频率 $f$。
$$\text{CPU clock cycles}=\text{IC}\times\text{CPI}$$
因此得到性能铁律（Iron Law）：
$$\boxed{\text{CPU time}=\text{IC}\times\text{CPI}\times T_c =\frac{\text{IC}\times\text{CPI}}{f}}$$
也可用量纲自检：
$$\frac{\text{instructions}}{\text{program}} \times\frac{\text{cycles}}{\text{instruction}} \times\frac{\text{seconds}}{\text{cycle}} =\frac{\text{seconds}}{\text{program}}$$
### 4.3 每个量由什么决定
讲义强调的总体对应关系如下：

| 因素 | 主要影响 | 原因 |
|---|---|---|
| 算法 | IC，也可能影响 CPI | 决定源代码级操作、I/O 操作及数据访问方式 |
| 编程语言与其实现 | IC、CPI | 同一源语句对应的机器操作和运行时支持不同 |
| 编译器 | IC、CPI | 指令选择、优化和调度改变指令数量与混合比例 |
| ISA | IC、CPI、$T_c$ | 指令表达能力、复杂度与实现约束不同 |
| 处理器与存储系统 | CPI、$T_c$ | 数据通路、流水线、冒险、Cache 与存储延迟影响执行 |
| I/O 硬件与操作系统 | 墙上时间、系统 CPU 时间、I/O 等待 | 决定 I/O 操作快慢及系统服务成本 |

若只问三个直接因子，可以简记为：

| 因子 | 不能忽略的决定因素 |
|---|---|
| IC | 程序与算法、编程语言及其实现、编译器、ISA |
| 平均 CPI | CPU 与存储系统实现，以及程序/编译器形成的指令混合和访问行为 |
| $T_c$ 或 $f$ | 工艺、电路、数据通路关键路径、流水线组织和 ISA 实现约束 |

> [!important] 不要背成机械的一一对应
> “CPI 只由硬件决定”是不完整的。
> 讲义明确指出平均 CPI 还受**指令混合（instruction mix）**影响；Cache 未命中、分支与数据依赖也会使同一处理器运行不同程序时呈现不同 CPI。
> 同样，ISA 不只影响 IC，也可能影响 CPI 与可实现的时钟周期。
### 4.4 平均 CPI 的加权计算
若第 $i$ 类指令有 $\text{IC}_i$ 条，每条平均需要 $\text{CPI}_i$ 个周期，则：
$$\text{Clock cycles}=\sum_{i=1}^{n}\text{IC}_i\times\text{CPI}_i$$
$$\text{IC}=\sum_{i=1}^{n}\text{IC}_i$$
$$\boxed{\text{Average CPI}=\sum_{i=1}^{n}\left(\frac{\text{IC}_i}{\text{IC}}\times\text{CPI}_i\right)}$$
权重是各类指令的**动态条数占比**，不是源代码中出现的次数，也不是把各类 CPI 简单做算术平均。

例如某程序动态执行 100 条指令，其中 50 条 ALU 指令各 1 周期、30 条访存指令各 3 周期、20 条分支指令各 2 周期：
$$\text{Cycles}=50\times1+30\times3+20\times2=180$$
$$\text{Average CPI}=\frac{180}{100}=1.8$$
若时钟频率为 $2\ \text{GHz}$，则：
$$T=\frac{180}{2\times10^9}=90\ \text{ns}$$
### 4.5 完整性能比较：低 CPI 不一定更快
**完整例题 2：同一 ISA、同一程序的两种实现。**

计算机 A 的时钟周期为 $250\ \text{ps}$，CPI 为 $2.0$；计算机 B 的时钟周期为 $500\ \text{ps}$，CPI 为 $1.2$。
同一程序在两台机器上的动态指令数均为 $I=2.0\times10^9$，比较性能。

A 的周期数和时间：
$$N_A=I\times2.0=4.0\times10^9$$
$$T_A=(4.0\times10^9)(250\times10^{-12}\ \text{s})=1.00\ \text{s}$$
B 的周期数和时间：
$$N_B=I\times1.2=2.4\times10^9$$
$$T_B=(2.4\times10^9)(500\times10^{-12}\ \text{s})=1.20\ \text{s}$$
相对性能：
$$\frac{\text{Performance}_A}{\text{Performance}_B} =\frac{T_B}{T_A}=\frac{1.20}{1.00}=1.20$$
所以 **A 更快，性能是 B 的 1.2 倍**。
B 虽然 CPI 更低，但每个周期持续的时间是 A 的两倍，最终总时间反而更长。

若只比较每条指令平均耗时，同一 $I$ 下也可得：
$$\frac{T_A}{T_B}=\frac{250\ \text{ps}\times2.0}{500\ \text{ps}\times1.2} =\frac{500}{600}=\frac{5}{6}$$
**常见误区：**只比较主频、只比较 CPI，或在 ISA 不同导致 IC 不同时仍擅自约去 $I$。
### 4.6 指令更少也可能不占优
讲义的两个编译代码序列说明：IC 与平均 CPI 必须一起看。

| 指令类别 | A | B | C |
|---|---:|---:|---:|
| 每类 CPI | 1 | 2 | 3 |
| 序列 1 的指令数 | 2 | 1 | 2 |
| 序列 2 的指令数 | 4 | 1 | 1 |

序列 1：
$$IC_1=2+1+2=5,\qquad N_1=2\times1+1\times2+2\times3=10$$
$$CPI_1=10/5=2.0$$
序列 2：
$$IC_2=4+1+1=6,\qquad N_2=4\times1+1\times2+1\times3=9$$
$$CPI_2=9/6=1.5$$
序列 2 的指令更多，但总周期更少。
若两者时钟周期相同，序列 2 更快；若编译到不同实现、时钟周期不同，则还要继续乘上各自的 $T_c$ 才能判断。

## 5. 功耗、三堵墙与多核转向
### 5.1 动态功耗、能量与散热
CMOS 电路的动态功耗常用下式近似：
$$\boxed{P_{\text{dynamic}}\approx\alpha C V^2f}$$
讲义写作 $\text{Power}=\text{Capacitive load}\times\text{Voltage}^2\times\text{Frequency}$，可把开关活动率 $\alpha$ 理解为并入了有效电容负载。

| 符号 | 含义 | 主要受什么影响 |
|---|---|---|
| $\alpha$ | 开关活动率，表示信号翻转的活跃程度 | 程序行为、电路活动与门控等 |
| $C$ | 被充放电的等效电容负载 | 晶体管、互连、电路规模与工艺 |
| $V$ | 工作电压 | 工艺、电路与功耗/性能管理 |
| $f$ | 时钟频率 | 设计目标、关键路径、电压与运行策略 |

- 动态功耗来自电容反复充放电，电压项是平方，因此降压历史上非常有效。
- 频率与电压在实际设计中并非总能独立调节，不能随意固定一个量后对另一个量作无限外推。
- 该式不是全部功耗：泄漏等会带来**静态功耗**，即使不翻转信号也可能耗电。
- **功率**的单位是 W，即 J/s；**能量**的单位是 J，近似有 $E=P\times t$。
- 降低功率不必然降低完成任务的能耗，因为执行时间可能变长；反之，更快完成任务也不保证总能量更低。
- 芯片能否持续工作还受封装、散热与温度约束，不能只看平均电功率。
**讲义数值例：**新 CPU 的电容负载为旧的 $0.85$ 倍，电压与频率都降低 15%，即也各变为旧的 $0.85$ 倍。

若只按讲义动态功耗模型比较：
$$\frac{P_{\text{new}}}{P_{\text{old}}} =0.85\times(0.85)^2\times0.85 =0.85^4\approx0.522$$
新动态功耗约为旧值的 52.2%。
这里共有**四个** 0.85 因子，因为电压要平方；漏乘一个电压因子是常见计算错误。
这也不表示整机功耗必定恰好为 52.2%，因为静态功耗与其他部件未包含在该模型中。

![[co-ch1-IhaQZkvp.png]]

图中可见主频不再延续早期的快速上升，功耗也受到明显约束。
它说明“继续提高频率”受到系统级限制，而不是说 CMOS 公式中某一个变量永远不变。
### 5.2 功耗墙（Power Wall）
**功耗墙**指功耗密度、泄漏和散热能力限制了继续依靠提频与增加开关活动来提升单核性能。

历史趋势可概括为：
1. 晶体管资源和开关速度曾随工艺快速进步。
2. 电压缩放逐渐难以延续过去的幅度，$V^2f$ 带来的功耗压力无法被轻易抵消。
3. 芯片可安全散出的热量有限，频率与电压不能无限提高。
4. 因此，单纯依靠更高主频获得性能的路径受到约束。
“不能再降压”是强调技术趋势与限制，不应理解为任何器件在任何条件下都绝对无法降低一点电压。
### 5.3 内存墙（Memory Wall）
**内存墙**指处理器执行能力提升与存储器延迟、带宽改善不同步，处理器越来越多时间可能耗在等待指令或数据上。
- 这里的“内存”问题不仅指 DRAM 容量不足，更关键的是**访问延迟和可用带宽**。
- CPU 周期很短，一次远端存储访问可能相当于许多个 CPU 周期。
- Cache 利用局部性，把常用数据放在更近、更快的层次，是缓解内存墙的核心方法。
- Cache 不能消除所有 miss，也不能让所有程序都变成计算受限。
- 后续将在 [[05 存储层次：Cache 与虚拟内存]] 展开存储层次。
### 5.4 指令级并行墙（ILP Wall）
**指令级并行（Instruction-Level Parallelism，ILP）**是同一条指令流中可以同时执行的操作程度。

限制来自：
- 真数据依赖使后续指令必须等待先前结果。
- 分支与控制依赖增加取指和调度难度。
- 存储访问延迟与依赖分析限制可并行窗口。
- 更宽的超标量、更复杂的乱序调度会增加硬件成本和功耗。
因此，乱序执行、超标量、VLIW 等技术不能无限从单一指令流中挖出有用于提升性能的并行性。
ILP 墙不是说“程序里完全没有并行”，而是说**可低成本、持续利用的并行性有限**。
### 5.5 为什么转向多核，又为什么多核不自动加速
讲义把单处理器性能受限归因于功耗、ILP 和存储延迟，并引出多核微处理器：
- 多核是在一个芯片上放置多个处理器核心。
- 与硬件自动发现 ILP 不同，利用多核通常需要显式并行编程或并行运行时支持。
- 程序员需要处理负载均衡、通信和同步。
- 若任务无法拆分，增加核心数不一定缩短单任务响应时间。
- 若拆分后通信开销过大，并行收益也可能被抵消。
所以多核是绕过单核限制的重要路线，不是“核心数翻倍，所有程序就翻倍快”的定律。

## 6. Benchmark、SPEC 与 MIPS 陷阱
### 6.1 为什么需要基准测试
**基准测试程序（benchmark）**是用来测量和比较性能的一组规定工作负载。

一个有用 benchmark 至少要说明：
1. 运行什么程序、输入什么数据、完成多少工作。
2. 测量的是墙上时间、CPU 时间、吞吐率还是能效。
3. 编译器、编译选项、操作系统与硬件配置是什么。
4. 如何汇总多个测试的结果。
“据说很像实际负载”只是设计目标，不代表对所有用户都有代表性。
编译器、库、输入规模和运行环境都可能改变结论。

执行时间通常是最直接的性能依据，但系统选择还可能同时关心成本、可靠性、功耗与 I/O，不能只追求一个跑分数字。
### 6.2 SPEC CPU：用比值和几何平均汇总
**SPEC（Standard Performance Evaluation Corporation）**开发 CPU、I/O、Web 等基准测试。
讲义以 **SPEC CPU2006** 为例：
- 运行一组被选定的程序，以执行时间测量性能。
- I/O 影响较小，因此重点反映 CPU 与相关存储层次的性能。
- 包含整数测试 CINT2006 与浮点测试 CFP2006。
- 将测试机结果相对参考机器归一化，再用几何平均汇总。
若第 $i$ 个测试的性能比值为：
$$r_i=\frac{T_{\text{reference},i}}{T_{\text{test},i}}$$
则 $n$ 个测试的汇总为：
$$\boxed{\text{Geometric mean}=\left(\prod_{i=1}^{n}r_i\right)^{1/n}}$$
参考机器执行时间与测试机执行时间不能颠倒：测试机更快时，$T_{\text{test},i}$ 较小，$r_i$ 应大于 1。
几何平均适用于这组归一化比值，但不等于“所有性能数据都永远应取几何平均”。
若目标是实际总运行时间，往往应直接对时间求和或按真实工作负载加权。

SPEC CPU2006 是讲义采用的历史案例，不应误写成当前最新 SPEC 套件。
### 6.3 SPECpower：性能还要除以功耗
讲义同时给出 SPEC Power Benchmark，用服务器在不同负载等级下的表现衡量能效：
- 性能指标为 `ssj_ops/sec`，表示服务器端 Java 业务操作速率。
- 功耗单位是 W，即 J/s。
- 综合指标把各负载等级的操作速率之和除以功耗之和。
$$\text{Overall ssj\_ops/watt} =\frac{\sum_i\text{ssj\_ops}_i}{\sum_i\text{power}_i}$$
其单位可理解为“每焦耳完成的操作数”，越大通常表示能效越好。
它不是把每个负载点的比值简单平均，也不是只测满载。

讲义中的 Xeon 示例揭示了**低负载不等于低功耗成比例下降**：

| 负载 | 功耗 | 相对满载功耗 |
|---:|---:|---:|
| 100% | 258 W | 100% |
| 50% | 170 W | 约 66% |
| 10% | 121 W | 约 47% |

负载降至 10%，功耗仍为满载的 47%，说明 idle 基础功耗不可忽略。
数据中心又常在中低负载运行，因此“让功耗更接近随负载成比例变化”具有实际价值。
### 6.4 MIPS 的定义
**MIPS（Millions of Instructions Per Second）**表示每秒执行多少百万条指令：
$$\text{MIPS}=\frac{\text{Instruction count}}{\text{Execution time}\times10^6}$$
代入性能铁律，可得到：
$$\boxed{\text{MIPS}=\frac{\text{Clock rate}}{\text{CPI}\times10^6}}$$
这里时钟频率必须用 Hz，执行时间必须用秒。
MIPS 中的 M 是 $10^6$，而存储容量语境中的 Mi 常指 $2^{20}$，二者不要混淆。
### 6.5 为什么高 MIPS 可能对应更差性能
MIPS 有三个关键盲区：
1. **不同 ISA 的一条指令完成的工作量不同。**跨 ISA 比较每秒指令数，可能是在比较两种不同“工作单位”。
2. **同一 CPU 上不同程序的 CPI 与指令混合不同。**MIPS 会随程序变化，不是固定硬件参数。
3. **MIPS 没直接给出完成目标任务所需的总时间。**编译器减少无意义指令时，甚至可能出现 MIPS 降低而任务更快的现象。
**完整例题 3：较低 MIPS 的机器反而更快。**

机器 X 与 Y 用不同 ISA 完成同一高级语言任务。
X 动态执行 $10^9$ 条指令，CPI 为 1，频率为 $2\ \text{GHz}$；Y 只需 $5\times10^8$ 条指令，CPI 为 2，频率为 $3\ \text{GHz}$。

X 的时间和 MIPS：
$$T_X=\frac{10^9\times1}{2\times10^9}=0.500\ \text{s}$$
$$MIPS_X=\frac{2\times10^9}{1\times10^6}=2000$$
Y 的时间和 MIPS：
$$T_Y=\frac{5\times10^8\times2}{3\times10^9} =\frac{1}{3}\ \text{s}\approx0.333\ \text{s}$$
$$MIPS_Y=\frac{3\times10^9}{2\times10^6}=1500$$
Y 的 MIPS 更低，但 $T_Y<T_X$，所以 Y 完成目标任务更快。
原因正是 Y 用不同数量、不同复杂度的指令完成同一工作。

> [!warning] 正确的使用边界
> 在同一 ISA、同一程序、动态指令数也相同的受控比较中，MIPS 可与执行时间形成较直接的关系。
> 但即使如此，最终仍应回到执行时间；跨 ISA、跨程序或跨指令混合时，不能用 MIPS 排名代替真实任务性能排名。

## 7. Amdahl 定律
### 7.1 局部加速不等于整体同比加速
**Amdahl 定律**用于估计只改进系统某一部分时，整体执行时间能减少多少。

设：
- 原总时间为 $T_{\text{old}}$。
- 被改进部分原来占总时间的比例为 $f$，所以 $T_{\text{affected}}=fT_{\text{old}}$。
- 未改进部分比例为 $1-f$，所以 $T_{\text{unaffected}}=(1-f)T_{\text{old}}$。
- 被改进部分自身加速为 $s$ 倍，即它的时间除以 $s$。
则：
$$T_{\text{new}}=T_{\text{unaffected}}+\frac{T_{\text{affected}}}{s}$$
$$\boxed{T_{\text{new}}=T_{\text{old}}\left[(1-f)+\frac{f}{s}\right]}$$
整体加速比为：
$$\boxed{S_{\text{overall}}=\frac{T_{\text{old}}}{T_{\text{new}}} =\frac{1}{(1-f)+\dfrac{f}{s}}}$$
$f$ 必须是**原总执行时间中的占比**，不是指令条数占比、代码行数占比或芯片面积占比。
$s$ 是局部加速比，不是整体加速比；这两个量最容易在代入时混淆。
### 7.2 完整 Amdahl 例题与极限
**完整例题 4：乘法运算优化。**

某程序原运行 $100\ \text{s}$，其中乘法占 $80\ \text{s}$，其他部分占 $20\ \text{s}$。
若优化使乘法部分自身加速 $4$ 倍，求新时间与整体加速比。

优化后的乘法时间：
$$T_{\text{multiply,new}}=\frac{80\ \text{s}}{4}=20\ \text{s}$$
未优化部分仍为 $20\ \text{s}$，所以：
$$T_{\text{new}}=20\ \text{s}+20\ \text{s}=40\ \text{s}$$
$$S_{\text{overall}}=\frac{100}{40}=2.5$$
也可直接代入 $f=0.8$、$s=4$：
$$S_{\text{overall}}=\frac{1}{0.2+0.8/4}=\frac{1}{0.4}=2.5$$
注意：局部加速 4 倍，整体只加速 2.5 倍。

若希望整体加速 $5$ 倍，新总时间必须是 $100/5=20\ \text{s}$。
但未改进部分本来就占 $20\ \text{s}$，于是要求：
$$20+\frac{80}{s}=20$$
这只有 $s\to\infty$ 时才在极限上成立，任何有限加速都无法做到。
因此讲义例的结论是：**不能通过有限倍数的乘法优化实现整体 5 倍加速。**
### 7.3 加速上限与优化决策
固定 $f$，令局部加速比趋于无穷：
$$\lim_{s\to\infty}S_{\text{overall}}=\frac{1}{1-f}$$
例如 $f=40\%$，即使把该部分耗时降到接近零，整体最多也只有：
$$S_{\max}=\frac{1}{1-0.4}\approx1.667$$
这解释了 **Make the common case fast**：
- 应优先优化在实际负载中占据大量时间的部分。
- “common”应按时间贡献和出现频率衡量，而不是凭代码长短猜测。
- 在无限加速局部之前，应先检查剩余部分是否已成为新瓶颈。
- 优化后时间比例会改变，若继续下一轮优化，应基于新的 profile 重新计算 $f$。
> [!warning] 常见误区
> - 把“局部提升 80%”直接当成“整体提升 80%”。
> - 用 $f=80\%$ 却忘记 $f$ 指原时间占比。
> - 把新时间写成 $T_{\text{old}}[1-f(1-1/s)]$ 后，又重复减一次未优化部分。
> - 认为无限加速某个占比不足 100% 的部件，就能无限加速整体。
> - 只根据理论公式决定优化，不测量真实程序与真实输入。

## 8. 计算机组成八大思想
教材与讲义在第 1 章给出八条贯穿后续课程的设计思想。
它们不是八个孤立口号，而是对“资源、抽象、常见情形、并行、流水、预测、层次、冗余”八类权衡的概括。
### 8.1 Design for Moore's Law：面向完成时的资源设计
**含义：**计算机设计周期较长，应预测产品完成时可用的工艺与集成资源，而不是只按项目开始时的条件设计。
- 晶体管资源增长曾使同面积集成更多功能、降低部分成本与功耗成为可能。
- 设计者要为未来的资源水平预留空间，例如存储容量、并行度和接口能力。
- 摩尔定律描述集成度趋势，不承诺主频、单线程性能或程序速度按同样速率增长。
- 当工艺缩放趋缓时，这条思想仍提醒设计者“面向快速变化的技术条件”，但不能机械套用旧翻倍速度。
### 8.2 Use Abstraction to Simplify Design：用抽象简化设计
**含义：**隐藏下层细节，向上层提供简单、稳定的模型。
- ISA 隐藏单周期、流水线和具体电路差异，是最典型的例子。
- 操作系统把设备细节封装为较统一的服务。
- 模块接口让大型系统能够分解设计、分别验证和替换实现。
- 抽象不是声称下层细节永远不重要；性能异常时仍需要跨层分析。
### 8.3 Make the Common Case Fast：加速常见情形
**含义：**优化常见情形通常比优化罕见情形带来更大的整体收益。
- 它可由 Amdahl 定律定量解释：原时间占比 $f$ 大，优化收益才可能大。
- 简单、常用的指令和寻址方式值得高效实现。
- Cache 命中是常见情形，应让命中路径快速，同时妥善处理 miss。
- “常见”必须由目标负载证明；对某个程序常见的路径，对另一个程序可能并不常见。
### 8.4 Performance via Parallelism：通过并行提高性能
**含义：**让多个操作真正同时进行，以增加单位时间完成的工作。
- 多核可并行执行多个线程或进程。
- 超标量在一个核内并行发射多条可执行指令。
- 向量或 SIMD 用一条指令同时处理多组数据。
- 并行需要付出通信、同步、复制资源和负载均衡成本。
- 并行与流水相关但不相同：并行强调多个资源同时工作，流水强调把一个任务分阶段并重叠不同阶段。
### 8.5 Performance via Pipelining：通过流水线提高性能
**含义：**把任务划分为若干阶段，让不同任务同时处于不同阶段，从而提高吞吐率。

讲义的洗衣例中，每人衣服都要经过洗涤 30 min、烘干 40 min、折叠 20 min，共 4 批。

完全串行时：
$$T_{\text{serial}}=4(30+40+20)=360\ \text{min}$$
理想流水安排下，烘干阶段最慢，为 40 min；按讲义时序：
$$T_{\text{pipeline}}=30+4\times40+20=210\ \text{min}$$
$$S=\frac{360}{210}=\frac{12}{7}\approx1.714$$
这里不能直接声称“三个阶段就有三倍加速”或“四个人就有四倍加速”。
流水线收益受最慢阶段、填充与排空时间、任务数量和额外开销限制。

进一步看：
- 单批衣服仍需经过 90 min 的三个阶段，流水主要改善多批任务的吞吐。
- 若阶段时间不均，快阶段会等待慢阶段。
- 真实 CPU 还增加流水寄存器和控制逻辑，并可能因冒险而停顿。
- 只有猜对“后续工作可持续进入流水线”等条件，吞吐优势才能体现。
### 8.6 Performance via Prediction：通过预测提高性能
**含义：**在结果尚未确定时先按较可能的情况继续工作，而不是空等。

成立条件有两个：
1. 预测具有足够准确率。
2. 预测错误后的恢复成本不过高。
典型例子是分支预测：先猜测控制流方向并继续取指，若猜错则清除错误路径并恢复。
预测不是无成本地预知未来，而是用“猜对的收益”抵消“猜错的代价”。
准确率、误预测惩罚和基础执行时间必须一起考虑。
### 8.7 Hierarchy of Memories：利用存储器层次
**含义：**把最快、最小、每位最贵的存储放在上层，把较慢、较大、每位较便宜的存储放在下层。
```text
寄存器
  ↓ 容量增大、每位成本降低、速度通常降低
L1 Cache（片上 SRAM）
  ↓
L2 / L3 Cache
  ↓
主存（DRAM）
  ↓
SSD / 磁盘等二级存储
```
- 层次结构试图同时接近“快”和“大且便宜”两个目标。
- 它依赖程序局部性：近期或附近使用过的信息更可能再次被使用。
- Cache 不是单纯“把全部数据复制一份”，还要解决放置、查找、替换和一致性问题。
- 越靠下通常容量越大、访问越慢，但具体系统应以实际组织为准。
### 8.8 Dependability via Redundancy：通过冗余提高可靠性
**含义：**物理部件总会失效，可用冗余部件或信息检测、掩蔽或恢复故障。
- 冗余计算或校验信息可以帮助检测错误。
- 备用模块可在主模块失效后接管，提高可用性。
- 多副本可降低单点故障导致数据不可用的风险。
- 冗余带来成本、面积、功耗和一致性开销。
- 冗余不自动等于安全，也不保证所有故障都能恢复；必须明确故障模型与恢复机制。

## 9. 我的理解与思考
> [!note] 个人归纳声明
> 本节是我根据讲义公式和例子做的**个人理解、归纳与延伸**，不是讲义原句，也不冒充老师的额外结论。
> 其中关于工程场景的讨论用于帮助理解；若课程考试有特定口径，应以课堂说明和指定教材为准。
### 9.1 性能铁律更像“联动系统”，不是三个独立旋钮
我最初最容易产生的误解，是把 IC、CPI、频率分别归给软件、硬件和工艺，然后认为可以独立优化。
实际上，同一个设计动作经常同时改变三个因子。

例如，把一条复杂指令拆成多条简单指令，可能让 IC 增加，却使数据通路更规则、CPI 或 $T_c$ 降低。
加深流水可能缩短 $T_c$，但分支误预测和冒险造成的额外周期又可能让 CPI 上升。
编译器减少指令数也可能改变指令混合，使平均 CPI 同向或反向变化。

所以我认为更可靠的思考顺序是：
1. 固定“完成什么工作”以及测量口径。
2. 分别估计优化前后的 IC、CPI、$T_c$。
3. 检查因子之间是否互相影响。
4. 最后比较三项乘积，而不是给单项 improvements 直接排名。
这也解释了为什么“主频更高”“指令更少”“CPI 更低”都只是局部证据。
只有总时间下降，才能支持目标任务上的性能结论。
### 9.2 延迟与吞吐率反映两种不同目标
我把响应时间理解为“一个请求走完全程要多久”，把吞吐率理解为“系统持续输出有多快”。
流水线特别适合说明二者：生产线可能每分钟产出更多产品，但某一件产品经过的工序和等待并未同比例减少。

在个人电脑交互场景中，用户更容易感知延迟；在服务器批处理场景中，吞吐率和能效可能更突出。
进一步说，平均吞吐率高也不能说明每个请求都快：少量请求可能因排队或同步等待很久。
这属于我对指标边界的延伸理解，不是本章讲义额外给出的排队论结论。

因此我看到“加核”“加深流水”时，会先问题目到底优化单任务、固定任务流的总完成时间，还是稳定状态下的单位时间产出。
三个目标相关，但并不等价。
### 9.3 Benchmark 是一个有边界的模型
我认为 benchmark 的价值不是给出机器永恒、唯一的性能排名，而是把测量变成可重复的实验。
它必须冻结程序、输入、编译选项与测量方法，否则“性能差异”可能只是实验条件差异。

SPEC CPU 尽量弱化 I/O，因此它适合回答特定 CPU 工作负载的问题，却不能直接代表数据库、网络服务或图形交互整机体验。
几何平均把多个比值压缩成一个数字，便于汇总，也会隐藏各子项差异：两台总分相近的机器，可能在不同应用上各有明显优势。

我的结论是：跑分应与目标负载相似，汇总分应与单项数据一起看。
如果把 benchmark 当成所有场景的普适真理，就把“测量工具”误用成了“性能本身”。
### 9.4 Amdahl 定律也是一份优化预算表
我把 $(1-f)+f/s$ 看成优化后的“时间预算”：没改的部分原样保留，改了的部分除以局部加速比。
它能迅速告诉我继续投入某个部件是否还有意义。

例如一个部件只占原时间 5%，即使把它优化到几乎不耗时，整体收益也有限。
相反，常见情形占比很大时，看似不惊人的局部改进也可能值得做。

但公式中的 $f$ 与 $s$ 不是凭空出现的，需要 profile 和实验支撑。
多核场景还可能引入原公式没有自动表示的通信、同步与负载不均，所以不能只用核心数替换 $s$ 就结束分析。
这些是我对公式使用边界的归纳。
### 9.5 ISA 稳定与实现进化可以同时进行
ISA 契约让我看到抽象与性能并不矛盾：接口稳定，反而给底层实现留下优化空间。
单周期、多周期和流水线可以在保持指令语义的条件下改变周期数与时钟周期。

不过，软件“不用改指令语义”不代表软件性能无需重新调优。
编译器调度、数据布局和并行方式仍要适应具体微体系结构。
我把这理解为：**抽象保证正确性的边界，不自动抹平性能的差异。**

## 10. 考点速查
### 10.1 概念辨析
1. **五类硬件部件**：输入、输出、存储器、数据通路、控制；后两者构成 CPU 核心。
2. **主存与二级存储**：主存通常易失，保存运行中程序与数据；二级存储非易失，跨运行保存信息。
3. **ISA**：软硬件接口，规定软件可见指令语义与机器状态；不是某种具体流水线实现。
4. **编译器与汇编器**：编译器把高级语言翻成低级代码，汇编器把汇编指令编码为机器指令。
5. **响应时间与吞吐率**：单任务延迟与单位时间总工作量，不是倒数关系。
6. **墙上时间与 CPU 时间**：前者包含等待、I/O 与 OS 影响；后者聚焦 CPU 实际服务于任务的时间。
7. **三堵墙**：Power / Memory / ILP，分别对应功耗散热、存储访问和单指令流并行度限制。
8. **多核**：需要并行编程、负载均衡、通信与同步，不保证单任务线性加速。
9. **Benchmark**：必须关注工作负载、输入、配置和汇总方法；SPEC CPU2006 是讲义案例。
10. **八大思想**：Moore、Abstraction、Common Case、Parallelism、Pipelining、Prediction、Memory Hierarchy、Redundancy。
### 10.2 公式与代入检查
1. **相对性能**：
$$\frac{P_X}{P_Y}=\frac{T_Y}{T_X}$$
2. **时钟关系**：
$$f=\frac{1}{T_c}$$
3. **CPU 时间**：
$$T=N_{\text{cycles}}T_c=\frac{N_{\text{cycles}}}{f} =\frac{IC\times CPI}{f}$$
4. **平均 CPI**：
$$CPI=\sum_i\left(CPI_i\frac{IC_i}{IC}\right)$$
5. **动态功耗**：
$$P_{\text{dynamic}}\approx\alpha CV^2f$$
6. **SPEC 比值的几何平均**：
$$G=\left(\prod_{i=1}^{n}r_i\right)^{1/n}$$
7. **MIPS**：
$$MIPS=\frac{IC}{T\times10^6}=\frac{f}{CPI\times10^6}$$
8. **Amdahl**：
$$T_{\text{new}}=T_{\text{old}}\left[(1-f)+\frac{f}{s}\right], \qquad S=\frac{1}{(1-f)+f/s}, \qquad S_{\max}=\frac{1}{1-f}$$
### 10.3 高频易错点
- 比较性能时把分子分母写反；先确认更快者的时间更短。
- 把“性能提高百分比”和“时间减少百分比”当成同一个数。
- 忘记动态指令数 IC 不等于源代码行数或静态指令条数。
- 把各类 CPI 不加权直接平均；权重必须是动态指令数占比。
- 只比较主频、CPI 或 IC 中的一项就判断整机性能。
- 在不同 ISA 下擅自约去 IC，或用 MIPS 直接判定谁更快。
- 动态功耗中漏掉电压平方，或把动态功耗当成包含泄漏的整机总功耗。
- 把功率 W 与能量 J 混为一谈，忽略 $E=P t$ 中的时间。
- 把几何平均误用于所有时间数据，或把 SPEC CPU 分数当作全场景整机性能。
- Amdahl 中把 $f$ 当成指令条数占比，或混淆局部加速 $s$ 与整体加速 $S$。
- 认为局部无限加速就能让整体无限加速；未改进部分决定上限。
- 流水线的阶段数不等于实际加速倍数，还要考虑最慢阶段、填充、排空和冒险。
- 单位换算错误：$250\ \text{ps}=0.25\ \text{ns}$，对应 $4\ \text{GHz}$。
### 10.4 解题流程模板
1. 写清目标任务、工作负载与时间口径。
2. 画出已知量，统一为 s、Hz、条、周期等单位。
3. 若比较机器，优先用 $T=IC\times CPI/f$ 求总时间。
4. 若有多类指令，先求总周期，再求平均 CPI。
5. 若只优化局部，明确 $f$ 是原时间占比、$s$ 是局部加速比。
6. 得出数值后检查方向：更快者时间更短，加速比应大于 1。
7. 最后写一句限制条件，例如“同一 ISA 与同一动态指令数”或“只考虑动态功耗”。
