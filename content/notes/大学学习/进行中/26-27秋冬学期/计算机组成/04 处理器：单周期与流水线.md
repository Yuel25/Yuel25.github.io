## 1. 单周期 CPU

- **每条指令都在一个时钟周期内完成**，故 $\text{CPI} = 1$。
- **时钟周期长度取决于耗时最长的指令**（通常是 `ld`）——这就是单周期 CPU 效率低下的根源：快指令也必须等满一个长周期。
- **内存必须拆成两部分**：**指令内存(instruction memory)** 与 **数据内存(data memory)**。因为默认的内存实现一个周期内只能读写一个位置，若不拆分，同一时刻处于取指和访存的两个动作会冲突。

![[co-ch4-8m8KK7Ar.png]]

> [!important] 控制信号的必要性
> 同一条数据通路上要跑不同的指令，**不能简单地把线连在一起**，必须用 **MUX** 做选择——而控制 MUX 的就是**控制信号(control signal)**，它由**控制单元(control unit)** 生成。

## 2. 指令执行五阶段

| 阶段 | 英文 | 做什么 |
|---|---|---|
| **取址** | Instruction Fetch (IF) | 按 `PC` 给出的地址从指令内存取出指令，`PC ← PC + 4` |
| **译码** | Instruction Decode (ID) | 分析指令字段，从寄存器堆读出 1~2 个源寄存器；产生控制信号、生成立即数 |
| **执行** | Execute (EX) | 主要是 ALU：R 型做算术逻辑；访存指令算地址；分支指令做比较 |
| **访存** | Memory (MEM) | 数据内存的读/写（仅 load / store） |
| **写回** | Write Back (WB) | 把结果写回寄存器堆 |

![[co-ch4-amfocLym.png]]

各阶段的细节：

- **EX**：
  - R 型：ALU 执行相应运算并输出结果；
  - 访存指令：ALU 计算「基址 + 立即数」得到真实地址；
  - 分支指令：ALU 把两个源操作数**相减**，用结果是否为 0（`Zero` 信号）判断是否相等。
- **MEM / WB 不是所有指令都需要**：只有 IF、ID 是**所有指令共有**的阶段；部分指令没有 MEM 或 WB。

> [!note] RISC-V 的「一次只做一件事」
> 不同于 x86，**RISC-V 没有任何一条指令在访存的同时对读出的数据做运算**——所以 MEM 阶段不重叠也算术，这让流水线设计简单很多。

### 2.1 Imm Gen（立即数生成器）

ID 阶段的一个模块，把指令中的立即数字段**符号扩展到 32/64 位**，供后续运算使用。

- **分支指令的立即数需要左移 1 位（补 0）**：因为 B 型立即数的最低位（`imm[0]`）是省略的（2 字节对齐），需要补回来。

### 3.2 控制信号

| 信号 | = 0（deasserted） | = 1（asserted） |
|---|---|---|
| `RegWrite` | — | 寄存器写入：把 Write data 写入 `rd` |
| `ALUSrc` | ALU 第二操作数来自寄存器堆 Read data 2 | ALU 第二操作数来自 Imm Gen（符号扩展后的立即数） |
| `PCSrc`（Branch） | 下一个 PC = `PC+4` | 下一个 PC = 分支目标地址 |
| `Jump` | 下一个 PC = `PC+4` | 下一个 PC = 计算出的跳转地址 |
| `MemRead` | — | 从数据内存读出数据，交由 `MemtoReg` 控制的 MUX |
| `MemWrite` | — | 把 Write data 写到 address 指定的内存位置 |
| `MemtoReg`（2 位） | `00`：**ALU 结果**送寄存器堆（R 型、I 型） | `01`：**数据内存读出值**（load）　`10`：**`PC+4`**（`jal` / `jalr`） |

### 3.3 ALU 控制：二级译码（2-level decode）

多种指令共用 ALU，采用**二级译码**：

1. **一级译码**：由 opcode 生成 7 个控制信号（上表的前 4 个 + Mem 相关）和 2 位的 `ALU_op`；
2. **二级译码**：由 `ALU_op` 与指令中的 `funct7`、`funct3` 共同决定 ALU 的具体操作。

### 3.4 单周期周期时间估算

> [!note] 例：估算周期时间
> 除以下延迟外忽略其他延迟：**内存 200 ps、ALU 与加法器 200 ps、寄存器堆访问 100 ps**。
>
> **方法**：单周期的时钟周期 = **最慢指令的关键路径**。逐条列出路径：
>
> | 指令 | 关键路径 | 时间 |
> |---|---|---|
> | `beq` | IM → RF读 → ALU | 200 + 100 + 200 = 500 ps |
> | R 型 | IM → RF读 → ALU → RF写 | 200 + 100 + 200 + 100 = 600 ps |
> | `ld` | IM → RF读 → ALU → **DM** → RF写 | 200 + 100 + 200 + 200 + 100 = **800 ps** |
>
> ⇒ 周期时间取 **800 ps**（由 `ld` 决定），其他指令都在浪费周期。
>

## 4. 流水线 CPU

### 4.1 从洗衣房说起

![[co-ch4-gXlLw0vr.png]]

流水线**不减少单个任务的时间**（甚至因为流水线寄存器而增加），但让多个任务的不同阶段**并行执行**，从而提升**吞吐率(throughput)**，最终减少完成所有工作的总时间。

两个设计约束：

- **平衡性**：各阶段耗时是否一致。可以通过合理地划分阶段让流水线更平衡（时钟周期由**最慢的阶段**决定，不平衡就是浪费）。
- **级数（深度）**：不是越深越好——每级之间的**流水线寄存器有固定延迟**，级数越多，这个固定开销占比越大。

> [!important] 流水线深度是权衡
> 加深流水线 ⇒ 时钟周期更短，但每级的「有效工作时间」被寄存器延迟稀释，且冒险（尤其是分支预测失败）的代价更大。这是典型的 *trade-off* 设计。

### 4.2 为什么 RISC-V 天生适合流水线

> [!note] RISC-V 架构是为流水线设计的
> - **所有指令都是 32 位**：取指和 PC 更新简单，不需要为变长指令做对齐处理。
> - **格式少而规整**：源寄存器与目标寄存器字段位置相同 ⇒ **译码与读寄存器可以在同一步完成**。
> - **Load/Store 寻址**：只有 load/store 访问内存，且**地址只在 EX 阶段计算、只在 MEM 阶段访存** ⇒ 各阶段职责清晰、不重叠。

### 4.3 流水线数据通路

![[co-ch4-MN5uM6ID.png]]

五级流水线用四个流水线寄存器串起来：

```text
IF/ID → ID/EX → EX/MEM → MEM/WB
```

> [!warning] 数据「从右往左」回流会造成冒险
> 上图中箭头从右往左的部分（**WB 写回寄存器堆**、**Branch 修改 PC**）正是三类冒险的来源——因为后面的指令会提前用到前面指令还没写回的结果。

`CPI ≈ 1`：理想情况下每个时钟周期都有一条指令进入 IF；但发生冒险时需插入 **bubble（气泡）**，CPI 会大于 1。

## 5. 结构冒险

**结构冒险(structure hazard)**：需要的**硬件资源正在被占用**。

最典型的例子就是内存：同一时刻 IF 阶段要取指令、MEM 阶段要读写数据。解决办法是**把内存拆成指令内存与数据内存两部分**，否则只能让其中一条指令暂停。

> [!note] 本题的「分解法」
> 本课程的流水线 CPU 通过拆分内存就基本消除了结构冒险；寄存器堆的「一个周期内两次读 + 一次写」也是靠**前半周期写、后半周期读**来避免冲突的（见下节）。

## 6. 数据冒险与前递

**数据冒险(data hazard)**：一条指令用到了前面指令尚未写回的数据。

> [!important] 只需要考虑前两条指令
> 在五级流水线中，当前指令（处于 EX）只可能与**前两条**指令产生数据冒险。原因是寄存器堆的读写时机：
> - **WB 阶段的写入发生在时钟上升沿**；
> - **ID 阶段的读取发生在时钟下降沿**；
> - 因此「前一条指令的 WB」与「当前指令的 ID」可以放在**同一个时钟周期**内完成。
>
> 如果没有这个优化（读写都在同一时刻），需要向后多考虑一条，就变成前三条。观察 forwarding 配图中阴影区域位置不同，正是这个时机差异的体现。
>
> 若不做任何优化（纯 stall），数据冒险最多需要 stall **2 个周期**。

### 6.1 前递 / 旁传（Forwarding / Bypassing）

![[co-ch4-RK45A20K.png]]

考察例子：第二条指令的源寄存器正好是第一条指令的目标寄存器 `x1`。与其等它写回，不如**提前把结果从 EX/MEM 或 MEM/WB 阶段的流水线寄存器直接送回来**——这就是**前递(forwarding)** 或**旁传(bypassing)**。

若不前递，则需要等 2 个时钟周期，EX 阶段才能拿到正确数据。

**前递的条件**：

![[co-ch4-mDBaG3zn.png]]

- 判断依据是「目标寄存器号相同」——因为 `add` 这类指令在 **EX 阶段结束**就有结果，而 `load` 要到 **MEM 阶段结束**才有。

> [!warning] 完整的判断条件还要加两条
> 原讲义截图里的条件**不完整**，必须补上：
> 1. 对应的 `EX/MEM.RegWrite` 或 `MEM/WB.RegWrite` 为真（即那条指令**真的会写**目标寄存器）；
> 2. 对应流水线寄存器的 `RegisterRd != x0`（**`x0` 不能作为前递源**，因为它的值恒为 0、不是真写）。
>
> 第 2 条如果漏掉，会出现「本应读 `x0` 却拿到前递值」的错误。

### 6.2 双重数据冒险（Double Data Hazard）

考虑：

```asm
add x1, x1, x2      # ①
add x1, x1, x3      # ②
add x1, x1, x4      # ③
```

③ 在 EX 阶段时，**同时**存在与 ① 的 MEM 冒险和与 ② 的 EX 冒险。此时必须使用**最新的**结果，所以：

> [!important] 优先级规则
> **EX 冒险优先于 MEM 冒险**。即：只有当「不能进行 EX 冒险的前递」时，才进行 MEM 冒险的前递。

完整判断条件（教材原文）：

```cpp
// EX hazard
if (EX/MEM.RegWrite and (EX/MEM.RegisterRd != 0)
    and (EX/MEM.RegisterRd == ID/EX.RegisterRs1))
        ForwardA = 10

if (EX/MEM.RegWrite and (EX/MEM.RegisterRd != 0)
    and (EX/MEM.RegisterRd == ID/EX.RegisterRs2))
        ForwardB = 10

// MEM hazard
if (MEM/WB.RegWrite and (MEM/WB.RegisterRd != 0)
    and not(EX/MEM.RegWrite and (EX/MEM.RegisterRd != 0)
        and (EX/MEM.RegisterRd == ID/EX.RegisterRs1))
    and (MEM/WB.RegisterRd == ID/EX.RegisterRs1))
        ForwardA = 01

if (MEM/WB.RegWrite and (MEM/WB.RegisterRd != 0)
    and not(EX/MEM.RegWrite and (EX/MEM.RegisterRd != 0)
        and (EX/MEM.RegisterRd == ID/EX.RegisterRs2))
    and (MEM/WB.RegisterRd == ID/EX.RegisterRs2))
        ForwardB = 01
```

## 7. 载入-使用冒险

![[co-ch4-ubBcnr9y.png]]

**载入-使用型数据冒险(Load-Use Data Hazard)**：当前指令要用**上一条 load 刚读出来的数据**。

> [!important] 即使有前递也必须 stall 一个周期
> 因为 load 的数据要到 **MEM 阶段结束**才拿到，而当前指令的 EX 阶段**更早**就想用。前递只能「把已经算好的结果提前送」，无法把尚未产生的数据提前送。
>
> ⇒ 必须 **stall 一个周期**，即插入一个 **bubble**。

**检测条件**：

$$ \text{ID/EX.MemRead}\ \&\&\ \big((\text{ID/EX.RegisterRd} = \text{IF/ID.RegisterRs1})\ ||\ (\text{ID/EX.RegisterRd} = \text{IF/ID.RegisterRs2})\big) $$

> [!note] 为什么考察 `ID/EX.RegisterRd`
> 检测 load-use 冒险时，load 指令的目标寄存器编号刚好传递到 **ID/EX** 这一级，而紧随其后的指令的源寄存器号还在 **IF/ID** 中——两者相比即可。

**实现 stall 的方式**：把当前指令转成 **`nop`**，从而让它的后续阶段变成 bubble（相当于把它「包裹」起来，不让它产生影响和控制信号）。

### 7.1 时钟周期计数示例

> [!note] 例：考虑数据冒险的时钟周期数
> 若不考虑冒险，$n$ 条指令需要 $n + (5-1)$ 个周期——例如 7 条指令需要 $7 + 4 = 11$ 个时钟周期。
> 但由于数据冒险，可能必须 stall 2 个周期。
>
> ![[co-ch4-msWVpgrK.png]]

### 7.2 指令重排（Code Scheduling）

既然 load-use 必须 stall，那就**在不改变结果的前提下调整指令顺序**，把不相关的指令插到 load 与它的使用者之间，从而填满那个 bubble。

![[co-ch4-juukFftc.png]]

> [!tip] 编译器视角
> 这是**编译器**的工作（指令调度），也是「流水线性能不只由硬件决定」的典型例证：同一份 ISA 代码，调度好坏能差出 20%+ 的 CPI。

## 8. 控制冒险

**控制冒险(control hazard)** / **分支冒险(branch hazard)**：是否跳转取决于上一条指令的计算结果，因此**下一条该取哪条指令**还不确定。

![[co-ch4-lcqgxCgf.png]]

**解决方案：分支预测(branch prediction)** —— 提前「猜」一条指令取来执行：

- 猜对了 ⇒ 流水线不留空泡，白赚；
- 猜错了 ⇒ 把错误指令的影响 **flush 掉**，并 stall 之后重新取正确的指令。

预测策略：

| 类型 | 做法 | 例 |
|---|---|---|
| **静态(static)** | 固定规则 | 基于典型分支行为（向后跳转的循环大概率继续循环 ⇒ 预测「跳」） |
| **动态(dynamic)** | 用硬件记录实际分支历史 | 记录每条跳转指令的跳转次数（如 2 位饱和计数器、分支历史表），在《计算机体系结构》中进一步讨论 |

> [!important] 控制冒险要插几个 bubble？取决于「跳转在哪个阶段决定」
> 默认（教材 datapath）认为分支的决策在 **MEM 阶段**处理，此时需要使下一条指令的 IF 发生在分支指令的 MEM 之后 ⇒ 插入 **3 个 bubble**。
>
> 但我们其实可以**更早知道**跳转结果：
> - 在 **EX 阶段**，ALU 的 `Zero` 输出就能告诉你是否相等 ⇒ 减少到 **2 个**；
> - 甚至可以把判断**提前到 ID 阶段**（增加一个比较器/ALU），只插 **1 个**。
>
> ⇒ **严谨的题目必须给出「跳转发生在哪个阶段」**，才能推定 bubble 数。

### 8.1 流水线数据通路与控制

控制信号在 **ID 阶段**全部译出，随后**逐级传递**到 EX/MEM/WB 各阶段的流水线寄存器；某个信号在之后不再用到时就不必继续传递（例如只有 WB 阶段用到的 `RegWrite` 需要一直传到 MEM/WB）。

## 9. 考点速查

1. **单周期**：CPI = 1，周期 = 最慢指令的关键路径（通常 `ld`）。内存必须拆成指令/数据两块。
2. **五阶段**：IF → ID → EX → MEM → WB；IF、ID 是所有指令共有。
3. **控制信号**：`RegWrite`、`ALUSrc`、`PCSrc`、`Jump`、`MemRead`、`MemWrite`、`MemtoReg`（2 位：00 ALU / 01 内存 / 10 PC+4）。
4. **ALU 二级译码**：一级 opcode → `ALU_op`，二级 `ALU_op` + `funct7` + `funct3` → 具体操作。
5. **Imm Gen**：分支指令的立即数要左移 1 位（补 `imm[0]=0`）。
6. **三类冒险**：结构（内存拆分）、数据（前递 + stall）、控制（分支预测）。
7. **前递条件三条**：寄存器号相同、`RegWrite` 有效、`Rd != x0`。
8. **优先级**：EX 冒险 > MEM 冒险（double data hazard 取最新结果）。
9. **load-use 必须 stall 1 周期**，因为数据要到 MEM 结束才有；检测看 `ID/EX.MemRead` 且 `ID/EX.Rd` 等于 `IF/ID` 的某个源寄存器。
10. **bubble 数与决策阶段**：MEM 决策 → 3 个；EX 决策 → 2 个；ID 决策 → 1 个（题目必须说明阶段）。
11. **周期数计算**：理想 $n + 4$（5 级流水线）；每 stall 一次 +1。
12. **代码重排**可以消除部分 load-use stall——这是编译器优化的战场。
13. **流水线提升吞吐率而非单条延迟**；深度是权衡（寄存器延迟摊薄 vs 冒险代价）。
